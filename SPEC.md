# SPEC — Telegram Referral Lead Finder

Спецификация согласованных требований. Документ описывает, **что** должно быть
построено; детали реализации фиксируются на соответствующих этапах.

Статус: требования согласованы. Разрешение Telegram на сбор информации
подтверждено владельцем проекта и считается выполненным; этот вопрос не
является блокирующим и далее в документе не рассматривается.

---

## 1. Цель проекта

Локальное Python-приложение, использующее официальный Telegram API через
протокол MTProto и библиотеку **Telethon**, получает **новые** сообщения из
заранее выбранных Telegram-чатов и сохраняет их локально.

Назначение: последующий поиск сообщений, в которых люди интересуются работой
курьером, просят реферальную ссылку, спрашивают, как устроиться, или задают
похожие по смыслу вопросы.

Предполагаемый масштаб: несколько десятков или сотен чатов, потенциально до
10 000 новых сообщений в сутки. Масштаб — предварительная оценка, а не
подтверждённая нагрузка.

---

## 2. Функциональные требования

### 2.1. Источник данных и авторизация
- FR-1. Источник сообщений — официальный Telegram API через MTProto с
  использованием Telethon.
- FR-2. Используется авторизованный **пользовательский** аккаунт.
- FR-3. Приложение подключается к Telegram, отслеживает новые сообщения и
  сохраняет их; отправка сообщений, рассылки и автоответы в MVP не входят.

### 2.2. Мониторинг чатов
- FR-4. На первом этапе мониторятся только чаты, в которых аккаунт уже
  состоит и имеет доступ к сообщениям.
- FR-5. Список чатов хранится в локальном файле `config/chats.txt`, по одному
  числовому ID на строку.
- FR-6. Получаются только **входящие новые** сообщения (событийная модель,
  без опроса истории).
- FR-7. Массовая загрузка старой истории не входит в MVP.

### 2.3. Обработка и сохранение сообщений
- FR-8. Новые сообщения сохраняются локально в SQLite.
- FR-9. Основные поля: `chat_id`, `message_id`, `date_utc`,
  `received_at_utc`, `text` и `sender_id` (если он доступен).
- FR-10. `text` содержит текст сообщения или подпись к медиа.
- FR-11. Сообщения без текста на первом этапе пропускаются.
- FR-12. Медиафайлы не скачиваются.
- FR-13. Дубликаты предотвращаются уникальным ключом `(chat_id, message_id)`.

### 2.4. Отказоустойчивость
- FR-14. Предусматриваются обработка ошибок соединения и использование
  штатных механизмов восстановления Telethon.
- FR-15. Абсолютная гарантия получения каждого сообщения **не заявляется** без
  соответствующей технической проверки.
- FR-16. Сбои восстановления и ошибки регистрируются в журнале.

## 3. Технические ограничения

- TC-1. Только официальный Telegram API через MTProto и Telethon. Автоматизация
  Telegram Desktop, OCR, ручной сбор и прочие альтернативы не рассматриваются.
- TC-2. Не применять маскировку автоматизации, обход ограничений Telegram или
  сокрытие характера использования API.
- TC-3. Не реализовывать собственный протокол `seq`/`pts` и ручные вызовы
  `getDifference`/`getChannelDifference`, пока не доказано, что штатных
  механизмов Telethon недостаточно.
- TC-4. Не добавлять периодические запросы истории в MVP.
- TC-5. Стек MVP: Python, Telethon, asyncio, SQLite, pytest, конфигурация через
  переменные окружения / `.env`. Дополнительные технологии — только с
  обоснованием.
- TC-6. Ограничения доставки обновлений Telegram/Telethon не выдумываются;
  существенные утверждения опираются на официальную документацию
  (core.telegram.org/api/updates, docs.telethon.dev).

## 4. Модель данных

Локальное хранилище — SQLite. Основная таблица `messages`:

| Поле | Тип | Обязательное | Назначение |
|---|---|---|---|
| `chat_id` | INTEGER | да | ID чата; часть составного первичного ключа |
| `message_id` | INTEGER | да | ID сообщения; часть составного первичного ключа |
| `date_utc` | INTEGER | да | Время сообщения (unix UTC) |
| `received_at_utc` | INTEGER | да | Время получения сообщения приложением |
| `text` | TEXT | нет | Текст сообщения или подпись к медиа |
| `sender_id` | INTEGER | нет | ID отправителя, если доступен |

- Первичный ключ: `(chat_id, message_id)`.
- Дедупликация обеспечивается уникальным ключом (например,
  `INSERT ... ON CONFLICT(chat_id, message_id) DO NOTHING`).
- Принцип минимизации данных: не хранятся имена, фотографии профиля, номера
  телефонов и прочие данные профиля без отдельного обоснования.
- Предусматривается возможность последующего удаления данных (ретенция); срок
  хранения определяется отдельно.

## 5. Требования к безопасности

- SEC-1. Сессия Telegram хранится **за пределами** репозитория; путь задаётся
  через `TG_SESSION_PATH`.
- SEC-2. Секреты (`TG_API_ID`, `TG_API_HASH`, файл сессии) не попадают в Git.
  `.gitignore` — дополнительная защита.
- SEC-3. Реальные идентификаторы чатов не попадают в Git; в репозитории
  хранится только `config/chats.example.txt`.
- SEC-4. Секреты не выводятся в журналы; логирование маскирует известные
  секретные значения.
- SEC-5. По умолчанию сообщения не передаются сторонним сервисам;
  медиафайлы не скачиваются. Единственное явно описанное исключение —
  передача очищенного текста в DeepSeek API (SEC-5.1–SEC-5.7).
- SEC-5.1. Допускается передача в **DeepSeek API** только очищенного текста
  сообщений, отобранных предварительным фильтром (`prefilter`), для смысловой
  классификации. Это единственный сторонний сервис и единственный случай
  передачи текста; прочие ограничения приватности не ослабляются.
- SEC-5.2. Перед отправкой из текста удаляются: `sender_id`, `chat_id`,
  `message_id`, `topic_id`, username, ссылки на профили и на исходные
  сообщения, телефоны, email, а также иные обнаруживаемые чувствительные
  данные.
- SEC-5.3. По умолчанию не передаются соседние сообщения, история автора и
  название чата; медиафайлы не передаются.
- SEC-5.4. Соответствие между ответом ИИ и исходным сообщением хранится
  локально и не передаётся.
- SEC-5.5. Онлайн-вызовы внешних моделей выключены по умолчанию и
  включаются только отдельным решением.
- SEC-5.6. Очистка текста по шаблонам не гарантирует полной анонимизации:
  человек может идентифицировать себя непосредственно в тексте сообщения.
- SEC-5.7. Секреты и локальные данные: API-ключи (например, ключ DeepSeek)
  хранятся в переменных окружения; файл сессии Telegram остаётся локальным,
  защищённым и исключённым из Git. Тексты сообщений, ответы API и личные
  идентификаторы не попадают в журналы и Git.

## 6. Требования к тестированию

- TEST-1. Unit-тесты без обращения к Telegram и сети: разбор конфигурации,
  маскирование секретов, работа с моделью данных.
- TEST-2. Интеграционные тесты с подменёнными компонентами и временной
  SQLite-базой: путь «событие → обработка → запись», повторная доставка
  (отсутствие дублей), пропуск сообщений без текста.
- TEST-3. Ограниченные живые тесты с реальным Telegram-клиентом — только после
  отдельного разрешения.
- TEST-4. Тесты изолированы: временные файлы и фиктивные переменные окружения;
  реальные локальные настройки не перезаписываются, реальные учётные данные
  не требуются.
- TEST-5. Проверяется, что секреты и реальные идентификаторы чатов не попадают
  в Git, а журналы не содержат секретов.

## 7. Границы MVP

**Входит:**

- подключение к Telegram через Telethon (пользовательский аккаунт);
- мониторинг выбранных чатов из `config/chats.txt`;
- получение новых входящих сообщений;
- извлечение текста/подписи и минимальных метаданных;
- локальное сохранение в SQLite;
- дедупликация по `(chat_id, message_id)`;
- журналирование технических событий и ошибок;
- восстановление после обычных отключений штатными средствами Telethon;
- базовые тесты.

**Не входит:**

- массовая загрузка старой истории;
- мониторинг чатов, где аккаунт не состоит;
- скачивание медиа;
- обработка правок и удалений сообщений;
- ИИ-классификация и определение кандидатов;
- автоматическая отправка сообщений и рассылки;
- Telegram-бот для уведомлений;
- веб-интерфейс;
- развёртывание на VPS и сложная инфраструктура/микросервисы.

## 8. Последовательность разработки

1. **Спецификация проекта** — настоящий документ.
2. **Подключение Telethon** и проверка получения новых сообщений.
3. **SQLite и дедупликация.**
4. **Обработка отключений** и проверка восстановления.
5. **Интеграционное тестирование** и оценка надёжности.
6. Отдельно согласуются **классификация сообщений, поиск кандидатов и
   уведомления**.

Пункты 2–6 пока только планируются и выполняются последовательно, каждый —
после отдельного подтверждения.

## 9. Критерии готовности будущих этапов

Общий процесс: **планирование → подтверждение → реализация одного этапа →
запуск тестов → проверка результатов → разрешение продолжить.**

- **Этап 2 — подключение Telethon.**
  - Получено реальное новое входящее сообщение из настроенного чата.
  - Регистрация обработчика входящих сообщений (`incoming=True`).
  - Корректное завершение процесса; понятное поведение при ошибках соединения.
  - Поведение штатного восстановления Telethon проверено и задокументировано.

- **Этап 3 — SQLite и дедупликация.**
  - Схема `messages` с первичным ключом `(chat_id, message_id)`.
  - Повторная доставка не создаёт дубликат.
  - Сообщения без текста пропускаются.
  - Unit- и интеграционные тесты зелёные.

- **Этап 4 — отключения и восстановление.**
  - После перезапуска дубликатов нет; пропуски (в пределах возможностей
    Telegram/Telethon) не создают дублей.
  - Сбои восстановления регистрируются.

- **Этап 5 — интеграционное тестирование и оценка надёжности.**
  - Прогон на реалистичном наборе; нет дублей; оценка полноты и задержек.
  - Явно задокументированы границы проверенного поведения.

- **Этап 6 — классификация, кандидаты, уведомления.**
  - Требования и критерии определяются отдельно перед реализацией.

Для каждого этапа критерии уточняются в момент планирования.

## 10. Открытые вопросы (влияют на архитектуру)

Принятые решения (не открытые вопросы): идентификаторы чатов — числовые ID по
одному на строку в `config/chats.txt`; `sender_id` сохраняется, если доступен;
мониторятся только чаты, в которых авторизованный аккаунт уже состоит;
абсолютная гарантия доставки не обещается, обнаруженные сбои восстановления
регистрируются в журнале.

Действительно нерешённый вопрос:

1. **Срок хранения сообщений и процедура удаления (ретенция).** Пока не
   определён. Решение необходимо принять **до полноценной эксплуатации
   системы**: требуется ли автоматическая очистка по возрасту и нужен ли
   механизм удаления по запросу. До принятия решения данные хранятся без
   автоматического удаления, при этом возможность удаления закладывается.
